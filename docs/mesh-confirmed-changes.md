# 组网地址变更的确认与恢复

已应用的组网更改前缀、节点地址或控制地址时，使用 `mesh.confirmed` 能力，主协议仍为 1。首次加入和不涉及这些地址的普通配置更新沿用原下发方式；旧节点继续支持这些操作。地址变更要求所有参与节点在线并支持该能力，否则在修改已应用文档前拒绝，并提示连接或更新节点。

## 顺序

1. 主控保留旧的已应用文档、节点确认状态和清理状态，将候选版本及恢复记录写入数据库。草稿保留；此时不把候选当成已应用版本，也不开始卸载。
2. 向所有参与节点（包括中转和主控本机节点）发送 `mesh.prepare`，同时携带候选配置和新管理 URL。节点先保存 `change.json`，包含旧配置、旧地址和本地回滚期限，不立即切换。
3. 所有节点准备成功后并发发送 `mesh.activate`，各节点延迟 2 秒切换。切换和定时器不依赖承载请求的控制连接。新管理地址不需要在旧网络上预先可达。
4. 主控重复读取所有参与节点的状态，要求同一变更 ID、候选版本已应用、数据面就绪且无错误。等待窗口为 100 秒，准备阶段也计入；未全部满足时不发确认。
5. 全部满足后发送 `mesh.confirm`。所有确认成功后才提交已应用文档与节点确认状态，最后执行清理。期间后来编辑的草稿不会被覆盖。

节点从准备时起有 180 秒期限。没有收到确认就恢复旧配置及旧管理地址；节点进程重启会在拨号前恢复持久记录。写回旧文件只是“恢复中”：运行过旧配置的节点必须再次上报旧版本确实应用，才能回答“已恢复”。

## 失败与重启

准备、切换、等待或确认中途失败时，主控保留草稿，撤回候选版本并向全部参与节点发恢复指令。已收到部分确认也能凭保留的旧配置补偿恢复。主控重启后从数据库恢复该意图；未取得恢复回执的节点继续显示“恢复中”，不会因期限过去而冒称成功。后台在节点重连后继续核实，恢复未完成时不下发下一次配置，也不通过重连补发绕过保护。

这不是跨机器的瞬时原子切换；执行与恢复均可能有短暂断连。节点进程、数据面或操作系统本身不可运行时，仍须等待其恢复，不能仅凭主控已发出恢复命令宣称网络恢复。真实跨平台网络及服务管理器行为需在相应环境验收。

## 移除成员与接入点

移除承载管理连接的成员前，必须先确认该节点能迁到新的接入地址。首选地址明确不可达而已有备用地址时，先尝试该备用，并保留向首选地址重试的待办。没有可达替代或节点离线时不写入新的已应用/清理状态，也不卸载，旧网络保持不变。这与能按期限恢复的地址变更不同。

合法组网前缀仍可用于数据面。若主控的组网地址不满足节点的明文 HTTP 策略，内建管理接入点显示不可用，并提示另配 HTTPS 接入点；不因此放宽公网 HTTP 策略，也不禁止该数据面前缀。
